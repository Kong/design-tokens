# Design Tokens Sandbox & Theme Builder — Agent Reference

Load this file before modifying anything under `packages/design-tokens/sandbox/`. It covers
the sandbox's surfaces, the shared infrastructure they depend on, and the reactivity /
testing pitfalls that have actually caused bugs in this codebase.

## What lives here

`packages/design-tokens/sandbox/` is a Vue 3 + `<script setup>` + Vite dev app (hash-routed,
`vue-router` with `createWebHashHistory` — required for GitHub Pages static hosting). It is
**not** Nuxt, has no SSR, and is not published — it only exists to let designers explore and
customize the token set. Run it with `pnpm sandbox:design-tokens` (builds tokens first, then
`vite sandbox`), or `pnpm sandbox:open` from `packages/design-tokens/` for the dev server alone.

Four routes (`router.ts`):

| Route | Component | Purpose |
|---|---|---|
| `/` | `pages/HomeView.vue` → `components/browser/TokenBrowser.vue` | Browse all tokens, preview under any repo theme |
| `/customize` | `pages/CustomizerView.vue` → `components/customizer/TokenCustomizer.vue` | Freeform editing of individual CSS custom properties, live-injected into a real page |
| `/theme-builder` | `pages/ThemeBuilderView.vue` → `components/builder/ThemeBuilder.vue` | Edit a theme's actual source files (`*.theme.json` + `*.alias.color.json`) |
| `/embedded` | `pages/EmbeddedView.vue` → `components/shared/SandboxUnifiedEmbed.vue` | **The one bookmarklet destination.** A single sidebar shell with a Customizer/Theme Builder mode switcher — see Surface 4 below. |

`/customize` and `/theme-builder` each still have a standalone `?embedded=1` variant of their
own component (legacy, kept working for bookmarklets dragged before the `/embedded` route
existed — see Surface 4's "Legacy standalone-embedded path" below). The **only** bookmarklet
generated by the app today points at `/embedded`.

## Surface 1 — Token Browser (`components/browser/`)

Read-only exploration tool. `composables/useTokens.ts` is the source of truth:

- `ALL_ENTRIES` — every customizable token (semantic/scale from `@tokens/js` + component from
  `KUI_THEMEABLE_TOKENS`), sorted with natural numeric ordering. **This is the canonical list**
  other composables (Customizer) iterate — never re-derive it.
- `THEMES` / `DEFAULT_THEME_ID` / `isThemeId` — the 4 repo themes (`classic-day`, `classic-night`,
  `electric-lime-day`, `electric-lime-night`) available for live preview, `classic-day` first
  and default (its values equal `ALL_ENTRIES`'s base values exactly).
- `resolveThemedEntries(entries, themeId)` — **pure function**, the single place that overlays a
  theme's declared token values onto a base entry list. A theme only declares what it actually
  overrides (`classic-day`/`classic-night` are semantic-only — zero component tokens; the
  `electric-lime-*` themes are exhaustive — every `KUI_THEMEABLE_TOKENS` entry). Any token a
  theme doesn't mention keeps its base value — this mirrors the real `var(--x, var(--fallback))`
  CSS behavior for an undeclared custom property. **Reused by both the Browser's theme picker
  and the Customizer's starting-theme picker** — do not duplicate this logic a third time.
- `fuzzyMatchTokens(query, ...targets)` — shared multi-term, separator-agnostic filter used by
  the Browser, Customizer, and Theme Builder search boxes.
- `useTokens()` composable returns per-composable-instance reactive state (`search`,
  `activeCategory`, `activeTheme`, `byCategory`, etc.) — safe to call multiple times, no shared
  module state here (contrast with the Customizer/Theme Builder, below).

## Surface 2 — Token Customizer (`components/customizer/`, `composables/useTokenCustomizer.ts`)

Freeform CSS-variable editor with a **live preview** injected into a real page (dev: same-origin
iframe via the Vite proxy; hosted: the bookmarklet sidebar, either directly via the legacy
standalone-embedded path or as one tab inside `SandboxUnifiedEmbed.vue` — see Surface 4).

**State is module-scoped, not composable-instance-scoped.** `overrides`, `customProps`, and
`startingThemeId` in `useTokenCustomizer.ts` are declared at module level (`const overrides =
reactive({})`, outside `useTokenCustomizer()`) specifically so they **persist across route
navigation** (e.g. leaving and re-entering `/customize`, or switching sidebar tabs — see Surface
4's `v-show`-not-`v-if` gotcha). This is intentional, but it means:
- Every call to `useTokenCustomizer()` anywhere in the app shares the *same* state — there is
  no per-instance isolation.
- Tests must explicitly reset this state between cases (see Testing section below) — nothing
  does it for you.

Key pieces:
- **`hosted` / `active` props.** Two independent, backward-compatible props (both default to
  today's standalone behavior — see Surface 4 for the full contract):
  - `hosted` — true when mounted inside `SandboxUnifiedEmbed.vue` rather than standalone.
    Suppresses this component's own `SandboxShell` header/close chrome (`chromeless`) and its
    own postMessage bridge; exposes `injectedCss`/`buildSrc` via `defineExpose` instead so the
    parent shell's single bridge can read them.
  - `active` — true when this tool is the one currently visible in the sidebar. Only matters
    when `hosted` (a non-hosted instance is always the only one). Gates the Cmd/Ctrl+F search
    shortcut so it doesn't keep intercepting the browser's native find while the other tool tab
    is the one showing.
- **Embedded tabs: Instructions / Tokens / Export** (`embeddedTabs`, only rendered when
  `isEmbedded`). `CustInstructionsPanel.vue` is a short, self-contained explanation of what the
  tool does and how to use it — added specifically because the bookmarklet sidebar has no other
  context for a first-time user. Defaults to the **Tokens** tab (not Instructions) — unlike Theme
  Builder, there's no mandatory setup step (no file to load) gating it.
- **Starting theme.** `startingThemeId` (module ref, default `DEFAULT_THEME_ID`) is the
  *baseline* the freeform editor starts from — pick Electric Lime Night and tweak individual
  tokens from there instead of re-entering every value by hand. `setStartingTheme(id)` validates
  against `isThemeId` and returns a boolean. Overrides/custom-props are **absolute values layered
  on top of whichever baseline is selected** — switching the starting theme must never clear or
  mutate them (`themedBaseEntries = computed(() => resolveThemedEntries(ALL_ENTRIES,
  startingThemeId.value))` feeds `visibleGroups` and `fullExportCss`; `overrides`/`customProps`
  are separate reactive maps applied on top, untouched by the theme switch).
- **No "overrides only" mode.** There used to be an "Overrides only / All tokens" inject-mode
  toggle; it was removed. The Customizer now **always** injects/previews/exports the full token
  set with overrides applied (`fullExportCss`). Don't reintroduce a partial-injection mode
  without checking why it was removed — it silently failed to reflect starting-theme switches
  when in "overrides only" mode, which is confusing UX for no real benefit.
- **There is no "share link" button anymore** (`CustSharePanel.vue` was deleted). Getting
  overrides out is now CSS-only: `CustOutputPanel.vue`'s copy/download buttons for the full
  computed CSS. Getting overrides *in* is `CustImportPanel.vue`, whose paste box/file-upload
  primarily accepts raw CSS (`importFromCss`) but still quietly accepts an old share URL or bare
  state code (`importFromCode`) for backward compatibility — that path is intentionally not
  promoted in the UI copy anymore, just kept working.
- **The `encodeOverrides`/`decodeOverrides`/`persistedUrl` machinery in `useTokenCustomizer.ts` is
  still fully in use despite the UI removal above — do not delete it.** Three separate things
  depend on it, none of which is "let the user copy a link to send to someone":
  1. `persistedUrl`'s own `watch([overrides, customProps, startingThemeId])` keeps the **standalone**
     `/customize` page's own URL hash in sync as you edit. This is what makes overrides survive a
     page reload there — `onMounted` restores from `?o=`/`?startTheme=`, and without the watch
     there'd be nothing in the hash to restore *from*. Reload-persistence, not sharing.
  2. `TokenCustomizer.vue`'s own `buildSrc()` (used by its embedded bridge) independently calls
     `encodeOverrides` + `setHashParams` to build the `src` string the bookmarklet persists per
     hostname (see Surface 4 / `preview-bookmarklet.ts`) — this is what makes re-opening the
     sidebar on the same site restore where you left off.
  3. `importFromCode` in `CustImportPanel.vue`'s paste box, per above.
- **The hash key is `startTheme=`, not `theme=`.** It's the Customizer's own starting-theme
  baseline — unrelated to the *Theme Builder* tool or its `*.theme.json` files, which it never
  touches. It was originally named `theme=`, which read as ambiguous once both tools began
  sharing one hash query string inside the unified bookmarklet sidebar (`?tool=theme-
  builder&theme=electric-lime-day` looks like it's telling Theme Builder to load a theme; it
  isn't, Theme Builder never reads this key at all). `getHashParam('startTheme') ??
  getHashParam('theme')` and `importFromCode`'s parser both still accept the legacy `theme=` key
  as a fallback, so links/state codes shared before the rename keep working — only the *write*
  side (the persistence watcher, `buildSrc()`) uses the new name exclusively. **Both write sites
  also explicitly pass `theme: null`** alongside `startTheme` — `setHashParams` only touches keys
  it's given, so without this a hash restored from an old `?theme=<id>` link would keep that
  stale value sitting in the URL forever, and resetting `startTheme` back to the default later
  (which omits it from the hash entirely) would let the read-side fallback silently resurrect the
  stale `theme=` value on the next reload — i.e. an explicit "reset to default" would silently
  un-reset itself. This shipped once in this same rename before being caught; if you add a third
  hash param that also carries a legacy alias, clear the old key explicitly, don't just stop
  writing it.
- **Share links. State round-trips through the URL hash** (`?o=` for the compressed
  overrides+customProps payload, `?startTheme=` for a non-default starting theme, `?selector=`
  for a custom injection selector). `encodeOverrides`/`decodeOverrides` handle the `c1:`-prefixed
  deflate-compressed format (falls back to plain base64 without `CompressionStream`).
  `importFromCode(raw)` accepts a full URL, a hash fragment, or a bare `o=` code, and applies
  both the theme param and `o=` if present — it returns `true` if *either* was successfully
  applied, not only when overrides decode. `importFromCss(css)` is separate: parses raw
  `:root { ... }` text and populates `overrides`/`customProps` only — it never touches
  `startingThemeId`.
- **Async watcher race guard.** The hash-sync watcher (`persistedUrl`'s) awaits `encodeOverrides`
  (variable-latency compression) — overlapping runs from rapid edits are guarded with a
  generation counter (`persistedUrlGeneration`) so a slow, stale run can't clobber a faster, newer
  one. The same pattern exists in `useEmbeddedBridge.ts`'s `post()` — copy it, don't invent a new
  one, if you add another async-then-write-shared-state watcher.
- **Embedded bridge.** `useEmbeddedBridge({ isEmbedded, css, buildSrc })` posts
  `kui-token-override` messages to the parent (bookmarklet host page) whenever `css` changes, via
  `watch(opts.css, post)`. **`isEmbedded` must be passed as a plain boolean, never a `computed`
  ref** — the composable checks `if (opts.isEmbedded)`/`if (!opts.isEmbedded)` directly against
  the value, so a ref object is always truthy regardless of its `.value` (this bit the `hosted`
  prop's `bridgeEnabled` once; fixed by making it `const bridgeEnabled = isEmbedded &&
  !props.hosted`, a plain boolean computed once at setup, not `computed(() => ...)`). `hosted`
  and `isEmbedded` are both static for an instance's lifetime, so no reactivity is lost.

Component contract gotcha (**bit us once, watch for the shape again**): `CustTokenRow.vue`
snapshots its displayed value into a local `ref` (`localValue`) on mount and only re-syncs it via
a `watch`. The row is keyed by `entry.cssVar` in `CustTokenGroup.vue`, so **the component
instance persists across a starting-theme switch** — it is never remounted. If the watch source
only tracks `props.overriddenValue` (the active override) and not `props.entry.value` (the
token's default, which *does* change when the starting theme changes), un-overridden rows go
stale and silently keep showing the old theme's values. The fix is to watch both:
`watch(() => [props.overriddenValue, props.entry.value] as const, ...)`. **Any prop that can
change without going through `overriddenValue` needs to be in that watch source** — this is the
general lesson, not just a one-off fix.

## Surface 3 — Theme Builder (`components/builder/`, `composables/useThemeBuilder.ts`, `composables/useBuiltInThemes.ts`, `lib/themeBuilderUtils.ts`)

Designer-oriented editor for a theme's **actual source files** (`*.theme.json` +
`*.alias.color.json`), loaded one theme at a time — either by picking one of the 6 repo themes
from a dropdown, or by file picker/drag-drop for any other theme. This is a different tool from
the Customizer — don't conflate them. Two-layer reactive state: alias palette overrides (cascade)
beat theme-file values; explicit token overrides beat the alias cascade. Color tokens are
alias-only (no freeform hex — picked via `AliasPicker.vue`); non-color tokens are freeform text.

- **`FileLoader.vue`'s two loading methods are mutually exclusive and commit-on-click, not
  commit-on-select.** Picking a theme from the "Load an existing theme" `<select>` only records
  `selectedBuiltInId` — it does **not** emit `load` immediately; the two upload drop-zones (now
  disabled + dimmed via `:disabled`/`.fl-drop--disabled`) stay inert until the user explicitly
  clicks **Load Theme**. Symmetrically, starting an upload (either file) disables the dropdown.
  A "Clear selection" control appears once either method has started (`hasSelection`) and resets
  both (`selectedBuiltInId` back to `''`, both file refs back to `''`) so the user can back out or
  switch methods without reloading the component. `emitLoad()` picks whichever method is ready —
  built-in wins if selected, since mutual exclusion means both can never be ready at once.
- **`composables/useBuiltInThemes.ts`** bundles the 6 repo themes' raw `*.theme.json` +
  `*.alias.color.json` source text at **build time** via Vite's `import.meta.glob('../../themes/
  */*.theme.json', { eager: true, query: '?raw', import: 'default' })` (and the alias-file
  equivalent) — resolved relative to the composable's own file location, so it works identically
  in dev and the static `BUILD_SANDBOX=true` GitHub Pages build with no runtime fetch, no copy
  step, no base-path/CORS concern. **The glob pattern argument must stay a static string literal
  at its own call site** — Vite resolves `import.meta.glob` via static analysis at build time, so
  wrapping the pattern in a parameterized helper makes it silently return `{}` at runtime. Only
  the *already-resolved* glob record (a plain `Record<string, string>`) is safe to hand to a
  shared helper (see `buildIdMap`). `BUILT_IN_THEMES` derives its id/label from `useTokens.ts`'s
  `THEMES` rather than duplicating theme metadata, and throws at module-evaluation time if any
  theme in `THEMES` is missing a bundled file pair — acceptable today (all 6 themes have both
  files) but means a half-scaffolded theme would white-screen the *whole app* (this composable is
  reached from the router via `FileLoader.vue` → `ThemeBuilder.vue` → `SandboxUnifiedEmbed.vue`),
  not just the Theme Builder tab.
- Raw-importing all 6 themes' source JSON adds real weight to the bundle (~700KB text,
  contributing to a >500KB main-chunk warning from Vite) — accepted for a design-tooling sandbox,
  but be aware it's paid by every route, not just `/theme-builder`, since the import chain is
  static all the way up to `router.ts`.
- **`hosted` / `active` props** — same contract as the Customizer's (above): `hosted` suppresses
  `SandboxShell`'s header/close chrome and this component's own bridge, exposing
  `injectedCss`/`buildSrc` via `defineExpose` instead; `active` is accepted for contract symmetry
  but currently unused (Theme Builder has no global-listener shortcut like Customizer's search).
- Always tabbed — `Instructions` / `Color aliases` / `Tokens` / `Export`, in both standalone and
  embedded/hosted contexts (no separate 3-column layout like the Customizer's standalone mode).
  Defaults to **Instructions** (unlike Customizer) because loading a theme is a mandatory first
  step there's no way around.
- **Per-sub-tab "modified" dot.** The `Color aliases` and `Tokens` tabs each carry a `modified`
  flag (`hasAliasOverrides`/`hasTokenOverrides`, both `computed(() => Object.keys(...).length >
  0)`) with its own tooltip — a small red dot (see `SandboxTabs.vue` below) so you can see at a
  glance which category actually has pending changes without opening it. `SandboxUnifiedEmbed.vue`
  separately marks its own top-level "Theme Builder" option modified using the combined
  `hasOverrides` (reading `useThemeBuilder()` directly — module-scoped state means it doesn't
  need to reach through `defineExpose` for this), so the cue is visible even while Theme Builder
  is the *inactive* sidebar mode, which is exactly when you're most likely to forget you have
  unsaved changes over there. Same dot pattern, ported to `SandboxModeSwitch.vue` (see Surface 4)
  for the top-level switch — kept as two near-identical implementations rather than sharing one,
  since the two widgets differ in every other way (`role="tab"` vs `role="radio"`, focus model).
- **"Reset all" is scoped per category, not global.** `TokenList.vue` and `PalettePanel.vue` each
  have their own "Reset all" button next to their "Show modified" toggle, each with its own
  confirm dialog, each clearing only its own category (`tokenOverrides` or `aliasOverrides`
  respectively — cleared directly by `ThemeBuilder.vue`'s `resetAllTokenOverrides`/
  `resetAllAliasOverrides`, which just delete keys off the already-exposed reactive maps; no
  composable change was needed). **Deliberately not the composable's existing (and still unused
  by any button) `resetAll()`**, which clears both categories together — wiring a Tokens-tab
  button to that would silently wipe alias edits the user can't see from that tab. If you ever
  do want a true "reset everything" affordance, it needs its own clearly-labeled control, not a
  repurposed per-category button.
- **Clear-filter buttons.** `TokenList.vue`'s and `PalettePanel.vue`'s search inputs now have the
  same custom SVG-X clear button (+ hidden native `::-webkit-search-cancel-button`) that
  Customizer and Token Browser already had — added for consistency; previously these two were the
  only search inputs in the app still relying on the browser's native (inconsistently-styled)
  clear-X.
- `lib/themeBuilderUtils.ts` — **pure, Style-Dictionary-free** functions, unit-tested directly
  in `themeBuilderUtils.spec.ts`: `resolveValue`/`parseAliasRef` (one-level `{color.alias.x.y}`
  lookup), `deriveEffectiveCss`, `flattenAliases`, `isColorToken`, `exportThemeJson`/
  `exportAliasJson`, plus the `BuilderToken` type (single source of truth). Keep new pure logic
  here, not inline in components, so it stays testable without mounting Vue.
  **`flattenAliases` sorts each family's steps numerically** (`Number(a) - Number(b)`), not via
  plain `Object.entries` enumeration order — JS enumerates canonical integer-index keys
  (`'10'`..`'120'`) ascending *ahead of* a leading-zero key (`'05'`, not a canonical integer index
  per spec), which would otherwise land `05` at the end of a family's chip row in
  `PalettePanel.vue` regardless of source insertion order. Same underlying JS quirk `stringifyOrdered`
  /`sortedStepFamily` below work around for the export path — three independent call sites hit
  this, so if you touch step ordering again, check both the render path (`flattenAliases`) and the
  export path (`sortedStepFamily`).
- `useThemeBuilder.ts` — module-scoped two-layer state (same module-scope-persists-across-nav
  pattern as the Customizer); `effectiveCss`; `initPersistence(host)` restores + debounced-
  persists the full state (theme+alias+overrides+filenames) to
  `localStorage['kui-theme-builder-state:<host|standalone>']`. **`initPersistence` unconditionally
  re-reads and overwrites in-memory `aliasOverrides`/`tokenOverrides` from localStorage on every
  call** — this is exactly why `SandboxUnifiedEmbed.vue` mounts Theme Builder with `v-show`, never
  `v-if` (see Surface 4): remounting would re-run `initPersistence` and could clobber an edit made
  in the last debounce window that hadn't flushed yet.
- **Storage-write failures are surfaced, not just swallowed.** Every `localStorage` read/write in
  the sandbox (`useThemeBuilder.ts`'s `persist()`/`initPersistence()`, and
  `preview-bookmarklet.ts`'s two try/catches) is wrapped so a `QuotaExceededError` or storage
  being disabled entirely (private browsing, some embedded contexts) never crashes the app — but
  each catch also `console.warn`s, and `persist()`'s failure sets a module-scoped
  `persistError: Ref<string | null>` that `ThemeBuilder.vue` renders as a small `.tb-persist-warning`
  banner. The point: the app must keep working from in-memory state either way (nothing here is
  allowed to throw), but *silently* losing reload-persistence is exactly the kind of failure a
  user only discovers after it's too late to do anything about, so don't reduce a future
  storage-write site back down to a bare empty `catch {}` — keep the warn/signal.
- **`OutputPanel.vue`'s Export tab has no inline CSS preview anymore.** The old large `<pre>`
  code block was replaced with two secondary-styled buttons — "Export computed CSS" (downloads a
  `.css` file) and "Copy" — both disabled when there's nothing to export. The "Export theme
  files" note reads *"Downloads the modified/unmodified `*.theme.json` and `*.alias.color.json`
  files"* (driven by a `hasOverrides` prop) — deliberately names the file **syntax**, not the
  user's actual filenames, so it doesn't imply the download is scoped to that specific theme.

## Surface 4 — Unified bookmarklet sidebar (`components/shared/SandboxUnifiedEmbed.vue`, `utils/preview-bookmarklet.ts`, `utils/buildBookmarkletHref.ts`)

**This is the only thing the app's bookmarklet points at.** One `javascript:` bookmarklet, one
sidebar iframe (`/#/embedded?embedded=1`), one `SandboxShell` header/close, one mode switcher
between Customizer and Theme Builder — replacing an earlier design that shipped two separate
per-tool bookmarklets. That design had a real bug: both bookmarklets' injected `message`
listeners validated sender **origin** only, not sender **identity** (`e.source ===
f.contentWindow`), so once a user had opened both on one hostname, either sidebar's messages
could satisfy the other's listener — corrupting each bookmarklet's own "last URL" localStorage
restore key and causing one bookmarklet to open the other tool. Collapsing to a single sidebar
removes the whole cross-talk class structurally (there's only ever one listener now); the
`e.source` check was also added to `preview-bookmarklet.ts`'s listener as defense in depth, since
already-installed legacy single-tool bookmarklets (static `javascript:` strings — they can't
self-update) could still collide with each other or a new one.

- **`utils/preview-bookmarklet.ts`** — the `BOOKMARKLET_TEMPLATE`, unnamespaced (`kong-sidebar`,
  `kong-sidebar-overlay`, `kong-sidebar-tab`, `window.__kongListener`, `kong-sidebar-
  url:<hostname>` restore key — no more `__STORAGE_NS__`/per-tool suffixes, since there's only
  one sidebar). Its `message` listener checks both `e.origin` (matches the sidebar iframe's own
  origin) and `e.source` (is literally that iframe's `contentWindow`) before applying
  `kui-token-override`/reacting to `kui-close`. Restoring the last-used `src` per hostname (via
  `localStorage`) is what makes "open whichever mode was last used, per domain" work — see below.
- **`utils/buildBookmarkletHref.ts`** — builds the one bookmarklet's `javascript:` href
  (`#/embedded?embedded=1`, replacing `__EMBED_URL__` in the template with the actual deployment
  origin). Both install surfaces (`CustPreviewPanel.vue`'s "One-time setup" card,
  `TokenBrowser.vue`/`BookmarkletModal.vue`'s modal) call this one function instead of each
  hand-rolling `BOOKMARKLET_TEMPLATE.replace(...)` — don't reintroduce that duplication.
- **`SandboxUnifiedEmbed.vue`** owns:
  - The single `SandboxShell` (`embedded`, title "Kong Design Tokens") — its `#tabs` slot holds
    the Customizer/Theme Builder `SandboxModeSwitch` (a segmented control, see below); its
    `#header-actions` slot holds the single global `SandboxPreviewToggle` (`compact`, see below).
  - `selectedTool` (`'customizer' | 'theme-builder'`, `composables/useSandboxMode.ts`'s
    `SandboxTool`/`isSandboxTool`), persisted into the hash as `?tool=`. **Theme Builder is the
    default** (`selectedTool` falls back to `'theme-builder'`, not `'customizer'`, when `?tool=`
    is absent) — and unlike the Customizer's own `startTheme=` (which still omits its default from
    the hash), `?tool=` is now **always written explicitly** for both values, via `watch(selectedTool,
    ..., { immediate: true })`. The `immediate: true` is required, not decorative: mounting already
    at the default and then re-selecting that same value is a same-value assignment, which a
    non-immediate Vue watch never fires for — without it, the hash would never get `tool=` written
    on a fresh mount. This is what "per-domain last-used-mode" restore actually rides on — the
    bookmarklet's own `kong-sidebar-url:<hostname>` restore key stores the full posted `src`,
    `tool=` included, so re-opening the sidebar on a site naturally reopens whichever tool was
    last selected there. No separate "last mode" storage key exists or is needed. `SandboxModeSwitch`'s
    `options` array also lists Theme Builder first, matching the default; `TokenBrowser.vue`'s two
    "try it" links do the same.
  - `previewEnabled` (default `true`, **not persisted** — matches the original per-tool toggle's
    behavior). A single global on/off switch, decoupled from `selectedTool`: switching tools never
    implies enabling/disabling, and toggling preview off never hides either tool's editor (you can
    keep editing while off) — it only stops pushing CSS onto the target page. This replaced an
    earlier design with a third "Off" tab in the mode switcher, which conflated "no tab selected"
    with "no injection," and read as more confusing than a dedicated toggle.
  - **The Customizer/Theme Builder switch is a segmented control (`SandboxModeSwitch.vue`), not a
    tab bar** (`role="radiogroup"`/`role="radio"`, one filled pill for whichever side is active).
    This replaced an even earlier design where this same switch was `SandboxTabs.vue` with a
    `prominent` prop (heavier active-tab styling) — tabs are the wrong widget here regardless of
    how heavily styled, since `role="tablist"` conventionally means "panels of one interface you
    can flip between," which is exactly the wrong mental model for two tools that must never be
    thought of as combinable. A real radiogroup gets "pick exactly one" for free, both visually
    (one continuous track, one filled segment) and for assistive tech. Each tool's own internal
    sub-tabs (Instructions/Tokens/Export, Instructions/Aliases/Tokens/Export) correctly stay
    `SandboxTabs` — those genuinely are switchable panels of one tool, not two mutually-exclusive
    tools, so a tab list is the right pattern there. `SandboxModeSwitch.vue` implements its own
    roving-tabindex arrow-key navigation (ArrowLeft/Right/Up/Down, Home/End) since a custom
    `role="radio"` widget doesn't get that behavior for free the way a native `<input
    type="radio">` group does — don't skip this if you touch the component, or it becomes a
    radiogroup in name only.
  - **One `useEmbeddedBridge` instance for the whole sidebar** — not one per child. `activeCss`
    is a `computed` that reads whichever child is `selectedTool` (gated by `previewEnabled`);
    `activeBuildSrc()` delegates to that child's own `buildSrc`. This is deliberate: an earlier
    draft gave each child its own bridge (gated by an `active` prop) plus a separate bridge for
    the "off" case, and that had two real bugs caught by adversarial review — the "off" bridge's
    `isEmbedded: true` fired unconditionally on every mount regardless of actual mode, and three
    independently-scoped `generation` counters could let a stale post from one bridge land after
    a newer post from another. A single bridge has one `generation` counter and no second
    instance to race against — don't re-split this without re-solving both problems.
  - **`defineExpose` auto-unwraps.** `TokenCustomizer.vue`/`ThemeBuilder.vue` expose `{
    injectedCss, buildSrc }` where `injectedCss` is a `computed`. Reading it through a template
    ref (`custRef.value.injectedCss`) gives the **plain unwrapped value**, not the `ComputedRef` —
    Vue's exposed-instance proxy auto-unwraps top-level refs on access, same as template/`this`
    access. `custRef.value?.injectedCss.value` (with an extra `.value`) silently reads `undefined`
    off a string and falls through to `?? ''` — always empty, no error, no warning. This exact bug
    shipped once; caught only because a test asserted actual non-empty CSS content, not just
    presence of a post. If you add a new exposed computed, don't add `.value` when reading it
    through a template ref.
  - `SandboxModeSwitch.vue`'s `modified`/`modifiedTooltip` per-option dot is a deliberate
    near-duplicate of `SandboxTabs.vue`'s same feature (see above) rather than a shared
    sub-component — the two widgets' markup/ARIA are different enough (`role="radio"` vs
    `role="tab"`) that sharing would mean threading a role/semantics flag through, for a few dozen
    lines of CSS. `SandboxTabs.vue`'s own top-level `prominent` prop (a heavier active-tab
    treatment it briefly had, before `SandboxModeSwitch.vue` replaced tabs entirely for this
    switch) was removed — don't resurrect it.
  - `SandboxPreviewToggle.vue`'s `compact`/`toolLabel`/`infoTooltip` props exist specifically for
    this header placement: `compact` drops the long-form hint text (there's no room for it in a
    header row); the visible label is just "Live preview: On/Off" (color-coded) — it does **not**
    also print the tool name, since the segmented control right below already names it more
    clearly, and an earlier iteration that repeated it ("Theme Builder Preview: Enabled" next to a
    "Theme Builder" tab) read as redundant. `toolLabel` still feeds the switch's `aria-label`
    ("Toggle live preview for Theme Builder") for screen readers. `infoTooltip` (an info icon +
    tooltip) is what actually explains scope: *"Only \<Tool\>'s changes are live on this page
    right now. Switch to the \<OtherTool\> tab above to preview those instead."*
- **Legacy standalone-embedded path.** `/customize?embedded=1` and `/theme-builder?embedded=1`
  (both components' own, non-`hosted` embedded rendering) are kept fully working, unchanged,
  specifically so bookmarklets dragged before `/embedded` existed don't break. Do **not** redirect
  them to `/embedded?tool=...` — that would risk breaking an in-flight session on an old
  bookmarklet mid-edit. There's no in-app nudge to re-install the new unified bookmarklet; this
  was a deliberate v1 scope call, not an oversight.

## Shared infrastructure

- **`lib/hashRouteQuery.ts`** — `getHashParam(key)` / `setHashParams(updates)` read/write query
  params *inside* the hash fragment (`/#/customize?o=abc`), because hash routing means
  `window.location.search` is always empty. `setHashParams` preserves unrelated params and
  calls `history.replaceState` — always go through this, never hand-roll `window.location.hash`
  parsing. This is also why `SandboxUnifiedEmbed.vue`'s `?tool=` and each tool's own `?o=`/
  `?selector=`/`?startTheme=` never collide — whichever writes second still preserves what the
  other already wrote.
- **`vite-preview-proxy.ts`** — Vite dev-only middleware, `/preview-proxy?url=<encoded>`. Strips
  CSP/X-Frame-Options so arbitrary target pages render in the Customizer's dev iframe; injects a
  `networkOverrideScript` that intercepts `fetch`/`XHR`/`history.*`/`location.*`/`<script src>`/
  `<link href>` so the proxied page's own sub-resource requests and SPA router stay inside the
  proxy origin; injects a `headScript` that posts `kui-frame-ready` on load and listens for
  `kui-inject-css`. Preserves the original URL's hash fragment (Node `fetch()` strips it before
  forwarding otherwise).
- **`composables/usePreviewBridge.ts`** — mode-aware (`iframe-proxy` in dev, `bookmarklet-popup`
  in production, `?preview=bookmarklet` forces the latter locally) bridge from a reactive `css`
  ref to the external page. iframe-proxy pushes via both `postMessage` (`sendCssToFrame`, works
  across navigation) and direct `contentDocument` injection (`injectIntoIframe`, belt-and-
  suspenders, same-origin only via the proxy). Its param is a generic `css: Ref<string>` — don't
  assume it's specifically "overrides"; it receives whatever the caller wants injected (currently
  always the full token set).
- **`composables/useEmbeddedBridge.ts`** — the bookmarklet-sidebar-side counterpart:
  `post()`/`close()`, posts `kui-token-override`/`kui-close` to `window.parent`. Has the
  generation-counter async-race guard mentioned above — reuse this pattern, don't reinvent it.
  **`isEmbedded` must be a plain boolean**, not a `computed` ref — see Surface 2's gotcha above;
  the composable itself was deliberately left unchanged (no `MaybeRefOrGetter` support added) in
  favor of Surface 4's single-bridge design, which needs no such reactivity.
- **`lib/cssUtils.ts`** — `applySelector` rewrites a `:root { ... }` block to a different
  selector for custom-scoped injection (e.g. `[data-theme="dark"]`). `hardenCssPrecedence`
  makes injected tokens win the cascade on an arbitrary target page: `!important` on every
  declaration + a specificity bump `:root` → `:root:root` (kept on the document root so tokens
  still inherit to teleported KModal/KToaster/etc.; deliberately *not* `:root body` or a bigger
  hammer). **Injection-only** — applied to the CSS pushed to the bookmarklet
  (`TokenCustomizer`/`ThemeBuilder` `injectedCss`) and the dev iframe preview
  (`CustPreviewPanel`), never to the copyable/exported block (which stays clean, no
  `!important`). Doesn't cover a target rule that sets a *consuming* property important without
  `var()`, or `@layer`ed important declarations.
- **`components/shared/SandboxShell.vue`** — shared header (title, Browse link when not
  `embedded`, close ✕ button when `embedded`), `#tabs` slot, scrollable `#default` body slot.
  `chromeless` prop (default `false`): when `true`, suppresses the `<header>` entirely (still
  renders `#tabs` — that's a tool's own internal navigation, not chrome) and switches its root
  height from `100vh` to `100%` so it fills the flex space `SandboxUnifiedEmbed.vue` gives it
  instead of re-claiming the whole viewport a second time. Used by `TokenCustomizer.vue`/
  `ThemeBuilder.vue` via `:chromeless="hosted"`.
- **`components/shared/SandboxTabs.vue`** — shared tab bar (`role="tablist"`/`role="tab"`), used
  only for each tool's own internal sub-tabs now (not the top-level Customizer/Theme Builder
  switch — see `SandboxModeSwitch.vue` below and Surface 4). `modified`/`modifiedTooltip` per-tab
  dot (see Surface 3) — a small red dot + hover/focus tooltip, falling back to the generic text
  "Modified" if a `modified: true` tab has no `modifiedTooltip`.
- **`components/shared/SandboxModeSwitch.vue`** — the segmented control (`role="radiogroup"`/
  `role="radio"`) used only for `SandboxUnifiedEmbed.vue`'s top-level Customizer/Theme Builder
  switch (see Surface 4 for why this is a radiogroup and not a tab list). Implements its own
  roving-tabindex arrow-key navigation and the same `modified`/`modifiedTooltip` dot pattern as
  `SandboxTabs.vue`, kept as a separate near-duplicate rather than shared since the two widgets'
  markup/ARIA differ throughout.
- **`components/shared/SandboxPreviewToggle.vue`** — the on/off switch that gates
  `injectedCss = previewEnabled ? hardenCssPrecedence(css) : ''`. Posting `''` clears the
  bookmarklet's `<style id="kong-design-token-overrides">` (listener coalesces `e.data.css||''`)
  → page reverts to native tokens WITHOUT clearing overrides; flipping back re-posts via the
  bridge's existing `watch(css)` (or, in `SandboxUnifiedEmbed.vue`'s case, its own explicit
  `watch(previewEnabled, () => post())`, since it isn't gating a child's own bridge). Two modes:
  default (long-form hint text below the switch, used by each tool's own standalone toggle) and
  `compact` + `toolLabel` + `infoTooltip` (single-line, used only by `SandboxUnifiedEmbed.vue`'s
  header placement — see Surface 4). In `TokenCustomizer.vue` the toggle must be excluded from
  `.cust-embedded-body > * { flex: 1 }` (it's a fixed-height header, not a growing tab pane) —
  see the `> .preview-toggle` override; the Instructions panel there needs no such exception since
  it manages its own internal scroll like the Tokens/Export panes do.

## State-management patterns & gotchas

1. **Module-scoped composable state persists across the whole app lifetime**, not just one
   component's mount. `useTokenCustomizer.ts` and `useThemeBuilder.ts` both do this deliberately
   (survive route nav, and — since Surface 4 — survive switching sidebar tabs too). If you add
   new module-level state, decide explicitly whether it should behave this way — and if it
   shouldn't, put it inside the composable function body instead.
2. **Any `ref`/state that snapshots a prop on mount must watch every prop that can independently
   change its resolved value** — not just the "obvious" one. `CustTokenRow.vue`'s bug (Surface 2)
   is the concrete example: watching `overriddenValue` alone missed `entry.value` changing via a
   starting-theme switch. When adding a new prop that affects a locally-cached value, ask "what
   makes this prop's *effective* value change without the prop itself notionally changing" and
   put all of those triggers in the watch source.
3. **Async watchers writing shared/exported state need a race guard** if the async work has
   variable latency and can be re-triggered before it resolves (e.g. compression, network). Use
   the generation-counter pattern from `useEmbeddedBridge.ts`'s `post()` / the customizer's
   `persistedUrlGeneration`.
4. **Non-destructive layering is a hard invariant for the Customizer**: switching the starting
   theme, importing a CSS file, etc. must never clear `overrides`/`customProps` *except when the
   import itself is explicitly a full-session replace* (`importFromCss`/`importFromCode` both
   intentionally replace, by design — that's different from a starting-theme switch, which must
   not). Any new feature that changes the "baseline" must go through `themedBaseEntries`/
   `resolveThemedEntries` and leave the override maps untouched.
5. **`useEmbeddedBridge`'s `isEmbedded` option must be a plain boolean, not a reactive ref** — it
   checks the option's truthiness directly, so a `computed()` is always truthy regardless of its
   `.value`. See Surface 2/4 above; this is the single most likely gotcha to hit again if a future
   feature wants "conditionally embedded" behavior.
6. **A template ref's access to a `defineExpose`d `computed` auto-unwraps** — read it as a plain
   value (`custRef.value.someExposedComputed`), never with a trailing `.value`. See Surface 4's
   `defineExpose` gotcha above.
7. **Theme Builder's `initPersistence(host)` unconditionally overwrites in-memory state on every
   call** — never mount `ThemeBuilder.vue` with `v-if` in a context where it might remount while
   "active" (i.e. anywhere it could coexist with unflushed edits); use `v-show`. See Surface 3/4.

## Testing conventions

- Spec files touching `window`/`document`/mounting Vue need `// @vitest-environment jsdom` as
  the first line (default is `node`).
- `useTokenCustomizer`/`useThemeBuilder`/`useEmbeddedBridge` register hooks inside `onMounted`, so
  call them inside a real mounted component (`mount(defineComponent({ setup() { ... } }))`), not
  bare — `onMounted` no-ops outside an active instance.
- `useTokenCustomizer`'s and `useThemeBuilder`'s state is module-scoped: reset it in `beforeEach`
  (`resetAll()`/`unload()` + `setStartingTheme(DEFAULT_THEME_ID)` + reset the URL hash), and
  **unmount every mounted wrapper in `afterEach`** — otherwise its `watch`/`onMounted` hooks keep
  running and racing against later tests' state. `useSearchShortcut.spec.ts` hit this exact bug
  with a plain `window.addEventListener` (not a composable) — same fix, unmount everything.
- Prefer `flushPromises()` (`@vue/test-utils`) over `await new Promise(r => setTimeout(r, 0))`
  when waiting on an async watcher. Stub `CompressionStream`/`DecompressionStream` to `undefined`
  in specs that need `encodeOverrides`/the embedded bridge's `buildSrc` to resolve on a
  microtask `flushPromises()` can drain (the deflate stream is a macrotask it can't await);
  `decodeOverrides` still round-trips the uncompressed format, so this doesn't break anything it
  touches.
- Testing a `window.confirm`-gated action (e.g. any "Reset all" button): `vi.spyOn(window,
  'confirm').mockReturnValue(true/false)`, and assert the emit/mutation happens only when `true`.
- `electric-lime-day`/`-night` are exhaustive (declare every token) — searching them for a
  token some theme "doesn't declare" finds nothing. Use `classic-day`/`-night` (semantic-only)
  for that, and assert the precondition directly rather than silently skipping via `if (found)`.
- When testing `SandboxUnifiedEmbed.vue`, the top-level Customizer/Theme Builder switch is
  `SandboxModeSwitch`, not `SandboxTabs` — only each hosted child's own internal sub-tabs are
  `SandboxTabs` now. A bare `wrapper.findComponent(SandboxTabs)` finds whichever child's sub-tabs
  render first in the tree, **not** the top-level switch; scope it explicitly, e.g.
  `wrapper.findComponent(TokenCustomizer).findComponent(SandboxTabs)`, and use
  `wrapper.findComponent(SandboxModeSwitch)` for the top-level switch itself.

## Verification checklist before calling sandbox work done

1. `pnpm build:tokens` (or let `pretest` do it) then `pnpm test` from `packages/design-tokens/`
   — full suite must pass.
2. `pnpm lint` (or `pnpm lint:fix`) on touched files.
3. `pnpm typecheck` — check only the
   errors on lines you touched; this sandbox has some pre-existing strict-null errors in older
   spec files that are out of scope for unrelated changes.
4. For anything touching live preview/injection behavior, **run the dev server and check it in
   a real browser** — reactivity bugs like the `CustTokenRow` one above, or the `defineExpose`
   double-`.value` bug (Surface 4), pass every unit test that doesn't specifically assert on
   *content* and only show up visually or under a content-specific assertion. Use
   `pnpm sandbox:open` from `packages/design-tokens/`, and if a port conflict, note the actual
   port Vite picks (it auto-increments past 5173/5174/...). Drag the bookmarklet from the Token
   Browser and exercise both sidebar tabs, the global preview toggle, and a page reload.
